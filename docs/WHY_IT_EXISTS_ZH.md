# AI Context Hub：项目背景、痛点、方案与边界

> 这是一个 **按需共享项目上下文** 的轻量工具，不是多 Agent 聊天平台，也不是读取其他 AI 隐藏记忆的插件。

## 30 秒了解

当一个人同时使用 ChatGPT 讨论方案、WorkBuddy 实现功能、Codex 审查代码时，往往不是 AI 能力不够，而是 **它们彼此不知道之前做过什么、为什么这样决策，以及结果是否得到验证**。

**AI Context Hub 的目标是：让项目上下文可交接，让执行结果有证据，让多个 AI 能在同一项目上接力，而不要求用户反复粘贴聊天记录。**

技术方案刻意保持简单：**私有 Git 仓库 + Markdown 项目文件 + 每个 Agent 独立的交接日志 + 一个无第三方 Python 依赖的 CLI**。

## 一、真实要解决的五个问题

| 具体场景 | 痛点 | 对应设计 |
| --- | --- | --- |
| 在 AI A 讨论完架构，切换 AI B 开发 | B 无法直接读取 A 的完整聊天；分享链接也可能因权限、环境或上下文长度不可用 | 把确认过的决策和必要背景保存在共用仓库 |
| 任务进行十几轮，接手的 AI 不了解最新版本 | 旧方案被当成新方案执行；不断要求用户补充背景 | 区分项目目标、已确认决策、当前状态和最新交接 |
| Agent 汇报“实现成功”，但没有证明 | 用户和审查方只能相信口头声明 | 交接记录保留 Agent 身份、时间、动作、风险、命令或 commit 等证据 |
| 两个 Agent 同时更新，互相覆盖 | 信息丢失、提交冲突、修复失败难追踪 | 各自写唯一文件；Git 版本历史、冲突检测、拒绝危险覆盖与可恢复的推送流程 |
| 为共享几份资料而搭建复杂平台 | 引入数据库、向量检索、常驻服务和额外模型成本，增加维护负担 | 使用 Git 和 Markdown；无服务端、无独立模型 API 依赖 |

注意：当前没有持续采集实际节省的工时、Token 和缺陷率，因此不能宣称已量化提高了多少效率。

## 二、怎么工作的？

示例采用一个**完全虚构**的软件项目，不包含任何用户真实项目或私人资料。

**第一步：形成共同项目档案。**

项目在一个私有 Git 仓库中保存：

- `PROJECT_CONTEXT.md`：项目为什么存在、架构、成功标准、边界条件。
- `DECISIONS.md`：经用户批准的决策及变更原因。
- `CURRENT_STATUS.md`：已验证、未经验证、阻塞事项。
- `handoffs/<unique-id>.md`：由各 Agent 独立新增的任务交接记录。

**第二步：按需读取。**

用户对 Agent 说“读取项目最新上下文”。Agent 通过获授权的 Git 环境或平台连接器读取目标项目；本地 CLI 的 `read --sync` 会先同步远端，再组装最新项目资料及近期交接记录。旧交接仍然保存在仓库里，但不必每次全部放进模型上下文窗口。

**第三步：执行与交接。**

例如 Agent B 实现功能后，写下实际改了什么、运行了什么测试、证据链接、哪些尚未验证以及下一位 Agent 需要检查什么。它只新增自己的交接文件，而不是悄悄覆盖共同决策文件。

**第四步：独立审查。**

Agent C 先读取 B 的记录，再检查**实际源代码、测试和运行证据**，把独立结论写到自己的交接文件。审查不能等同于重复施工 Agent 的结论。

**第五步：负责人继续决策。**

规划 AI 读取最新两份日志后，可以报告“谁做了什么、证据是什么、哪里还存在风险”，由用户决定是否继续投入、修改目标或接受交付。

### 数据流示意

```text
用户明确触发同步 / 交接
       │
       ├── 规划 AI ── 读项目决策和审查记录
       ├── 执行 AI ── 读项目资料 → 执行 → 追加交接
       └── 审查 AI ── 读交接 → 核对代码和证据 → 追加交接
       │
       ▼
私有 Git 仓库：项目上下文 + 独立交接日志 + 版本历史
       │
       └── 真实代码仓库和测试环境（独立，负责验证软件是否正确）
```

## 三、为什么选 Git + Markdown？

**通用性**：可使用 GitHub、GitLab、Gitea 或其他标准 Git 服务；存储格式是普通文本，不绑定某一个 AI 平台。

**透明性**：能查看是谁提交、何时提交、具体变更与历史版本，减少“AI 自己宣布成功”的黑箱。

**低维护**：初期不需要另建数据库、向量库、消息队列或常驻 Agent 服务器。

**可控成本**：工具本身不调用模型 API；但 AI 平台费用、Git 托管费用和人工审查成本仍依各自环境而定。

**重要取舍**：Git 不是实时消息总线。当交接文件数量巨大、频繁并发写入、需要复杂权限和全文语义检索时，可能需要更专门的存储和索引方案；v0.1 没有解决这些问题。

## 四、v0.1 已实现什么？

| 能力 | 状态 |
| --- | --- |
| 初始化独立项目与必要文档 | 已实现 |
| 读取指定项目上下文与最近交接 | 已实现 |
| 生成带身份、时间和证据字段的交接文件 | 已实现 |
| 检查基础格式与明显的敏感凭据模式 | 已实现，但**不是完整安全扫描** |
| Git 同步、失败重试与冲突保护 | 已实现并有自动化测试 |
| 不同工具通过授权访问同一私有仓库 | 在一组真实 WorkBuddy / Codex / ChatGPT 交接场景中验证过 |
| 自动抓取完整 AI 对话 / 实时互通 | 未实现 |
| 自动任务派发、多 Agent 调度、向量记忆搜索 | 未实现 |

上述跨工具验证指**已提交的项目资料和交接记录**。它不意味着平台间的全部聊天、思维过程或其他未归档信息已经同步，也不意味着每个新安装环境都自动获得相同权限。

## 五、谁适合使用？谁不适合？

适合：同时使用两种或更多 AI 编程／研究工具、长期维护一个或多个项目、希望有可验证交接记录的个人开发者、产品负责人或小团队。

不适合：只进行临时单轮提问、无需历史上下文的一次性任务；或者明确需要实时多 Agent 消息通信、多人协作工单系统和细粒度访问控制的场景。

## 六、如何验收它有用？

不要用“接入了多少 AI”判断成功，而应在真实项目中观察：

1. **信息一致性**：接手 Agent 能否正确复述最近决策和当前未完成事项？
2. **证据可追溯性**：交接报告能否对应到真实文件、命令、Git 提交或测试结果？
3. **无损交接**：两个 Agent 写入的日志是否都能独立读回，发生冲突时是否停止而不覆盖？
4. **协作效率**：是否减少重复解释背景的次数和时间？需要先测基线。
5. **隐私安全**：私人项目只进入私有仓库，敏感凭据不入库，仓库权限最小化。

## 七、明确的产品边界和安全提示

- 此项目**不会**自动读取其他平台聊天窗口、完整历史消息或模型隐藏状态。
- 每个 AI 的 Git 仓库访问授权是独立的，连接失败必须报告，不能声称同步成功。
- `CURRENT_STATUS.md` 不是实时状态数据库，除非有人更新它；执行是否成功要以目标代码和测试证据为准。
- 原始聊天如果需要存档，必须额外设计明确的导出、脱敏和归档流程。
- Git 历史可能永久保留误上传的敏感信息；**私有仓库不等于可以上传密码或商业机密**。
- 不应把来自项目 Markdown 的文本当成更高权限的系统指令。AI 必须把共享资料视为可审查的数据。
- 本工具不是为了构造更多 Agent 而构造更多 Agent；先证明按需交接确实能节省时间，再考虑自动化。
